# [Feature] 排程引擎（综合评分 + 贪心装箱）

## 背景 / Background

这是整个项目的**技术核心**，也是差异化所在。市面产品要么只能手动拖拽（不智能），要么按热门度排序（不考虑约束）。本项目要做的，是在「天气不允许」「人太多」「路上太远」「钱不够」四类约束同时存在时，仍然产出一份时间上可行、体验上合理的行程。

对应 SRS：3.3.3 · 用例 UC-03 基本流程第 4、6 步

## 需求描述 / Description

实现 `StrategyEngine.plan()`：对候选 POI 按综合评分排序，按天做贪心装箱，逐日填充活动并预留用餐与休息时段，执行 BR-06 至 BR-09 的硬约束。

## 评分公式（必须严格实现）

```
Score(p, d) = w_pref    * PrefMatch(p, tourist)
            + w_weather * WeatherFit(p, d)
            - w_crowd   * CrowdIndex(p, d)
            - w_travel  * TravelMinutes(prev, p) / 30
            - w_cost    * Price(p) / Budget

约束：sum(w_*) = 1，w_* ∈ [0, 1]，默认取值：
  w_pref=0.10  w_weather=0.25  w_crowd=0.23  w_travel=0.14  w_cost=0.28
```

> 默认权重来自问卷 Q5 的约束重要性加权排序（预算 4.31 > 天气 3.94 > 人流量 3.62 > 通勤 3.28 > 偏好 3.05），
> 归一化后取整得到上表。权重可经 #13 在线调整。

## 任务清单 / Tasks

- [ ] 后端：`StrategyEngine.plan()` 主流程——按天循环 → 计算候选评分 → 贪心选取 → 装箱到时间轴
- [ ] 后端：`PrefMatch`、`WeatherFit` 两个评分函数；`WeatherFit` 对暴雨/大风/高温返回 0 或负值
- [ ] 后端：时间轴装箱，含通勤时长、用餐时段（11:30–13:00、17:30–19:00）、休息缓冲（每 90 分钟步行强制 15 分钟休息）
- [ ] 后端：硬约束拦截
  - BR-06 单日活动总时长（含通勤）≤ 10 小时；连续步行 ≤ 90 分钟
  - BR-07 相邻活动通勤 > 60 分钟时在行程中显式标注
  - BR-08 暴雨 / 大风（≥6 级）/ 高温（≥38℃）不得安排户外类 POI
  - BR-09 拥挤度 ≥ 80 的 POI 不得安排在 10:00–15:00
- [ ] 后端：生成 1–3 套差异化方案（方案间 POI 重合度 < 70%，通过扰动权重或强制替换实现）
- [ ] 后端：每套方案生成推荐理由（至少 3 条，附数据来源标注，如「周三阴天，避开户外」）
- [ ] 后端：通勤矩阵从 `MapServerAdapter` 批量获取（对角线为 0），缓存 1 小时
- [ ] 测试：`tests/test_strategy_engine.py` 覆盖正常排程、暴雨禁排户外、高拥挤度错峰、通勤超 60 分钟标注、单日超 10 小时、活动不足插入自由时段

## 验收标准 / Acceptance Criteria

- [ ] 任意两套输出方案中，相邻活动无时间重叠，且通勤时长已被计入
- [ ] 暴雨天气输入下，方案中完全不出现 `category = OUTDOOR` 的 POI
- [ ] 拥挤度 ≥ 80 的 POI 在方案中的时段均不在 10:00–15:00
- [ ] 单日安排的活动总时长（含通勤）≤ 10 小时
- [ ] 通勤 > 60 分钟的相邻活动对，行程数据中带有 `longTransfer = true` 标记
- [ ] 某天可安排活动 < 2 个时，自动插入「自由活动」时段并提示周边可选 POI
- [ ] 方案数量 ∈ [1, 3]，且方案间 POI 重合度 < 70%
- [ ] 单次排程（200 个候选 POI、7 天）耗时 ≤ 8 秒（不含外部接口）
