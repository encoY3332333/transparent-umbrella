# [Feature] 可行性校验与预算降本迭代

## 背景 / Background

排程引擎给出的是「理论上最优」，但用户真正能用的行程必须满足两个条件：时间上走得通、钱够花。问卷 Q6 显示 46.9% 的受访者遇到过「实际花费超预算」；Q5 里预算的重要性排第一。所以超预算不能只提示一句「已超出」，必须给出可执行的降本路径。

对应 SRS：3.3.3 · 用例 UC-03 基本流程第 7–8 步

## 需求描述 / Description

对生成的行程做四类校验（时间冲突、预算超限、开放时间、天气约束），超预算时按固定顺序迭代降本，输出最终方案与降本建议。

## 降本迭代顺序（必须严格按此顺序）

```
1. 住宿降档（舒适 → 经济，同区域替换）
2. 付费景点替换为同类别免费景点
3. 缩短天数（从最后一天往前删，保留首尾两天）
循环，最多 30 次迭代（STRATEGY_MAX_ITERATION）
```

## 任务清单 / Tasks

- [ ] 后端：`FeasibilityChecker.validate(itinerary)` 返回结构化校验结果（冲突列表 + 严重级别）
- [ ] 后端：时间冲突检测——相邻活动重叠、超出 POI 开放时间、通勤时长不足
- [ ] 后端：`BudgetCalculator.summarize(itinerary)` 按交通/住宿/门票/餐饮四类汇总，计算占用率与结余
- [ ] 后端：`BudgetIterator` 实现三步降本迭代，每步记录「做了什么改动、省了多少钱」
- [ ] 后端：降本建议生成（至少 3 条，含预计节省金额）
- [ ] 后端：迭代达上限仍未达标时，输出超预算方案 + 明确标注超支金额
- [ ] 页面：预算环形图（四类占比）+ 结余条 + 超预算时的橙色预警条
- [ ] 测试：`tests/test_budget.py` 覆盖四类求和、零预算、超大金额、单项为 null
- [ ] 测试：`tests/test_budget_iterator.py` 覆盖一次降本成功、三次降本成功、无法降本（输出超预算方案）

## 验收标准 / Acceptance Criteria

- [ ] 预算四类明细之和等于行程总费用，误差 ≤ 1 元
- [ ] 预算环形图四类占比之和为 100%（允许四舍五入误差 1%）
- [ ] 超预算时给出 ≥ 3 条降本建议，每条含可量化的节省金额
- [ ] 降本迭代严格按「住宿 → 景点 → 天数」顺序执行（可通过日志断言顺序）
- [ ] 迭代 30 次仍未达标时，返回方案但标记 `overBudget = true` 与超支金额
- [ ] 时间冲突检测能识别：活动重叠、超出开放时间、通勤不足三种情况
- [ ] 存在未定价活动时，该项计入「预估」并在明细中标注「待确认」
