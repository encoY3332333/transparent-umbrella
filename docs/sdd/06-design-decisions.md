# 第 6 章 关键设计决策

本章不是"我们用了什么技术"的清单，而是 7 个**当时存在真实备选方案、且选错会有明显代价**的决策。每一条写四件事：背景、备选、选择、代价与复审条件。

完整论证见 `docs/adr/ADR-001 ~ 007`，本章只做交付级摘要，并补充"落地证据"（指回代码，便于答辩核查）。

## 决策总览

| 编号 | 决策 | 备选方案 | 代价 | 落地证据 | 状态 |
|---|---|---|---|---|---|
| ADR-001 | JWT（HttpOnly Cookie 载体） | Session + Redis | 无法主动踢人；需依赖 Cookie 策略 | `core/security.py`、`api/auth.py` | ✅ |
| ADR-002 | 排程引擎拆 3 子模块、契约先行 | 一人做完整引擎 | 需维护 `protocols.py` 契约 | `engine/`、`services/engine_bridge.py` | ✅ |
| ADR-003 | 贪心装箱 + 综合评分 | 整数规划 / DP | 不保证全局最优 | `engine/packer.py`、`engine/scorer.py` | ✅ |
| ADR-004 | 外部数据全部服务端代理 | 前端直连第三方 | 服务端承担配额与超时成本 | `adapters/base.py`、`call_budget.py` | ✅ |

## 6.1 ADR-001 认证方案：JWT + HttpOnly Cookie

**背景**：UC-01 需要登录态；BR-03 要求"未登录也能生成行程"。系统是单体服务端渲染，但页面里仍有 XHR/HTMX 局部请求。

**备选**：Session + Redis（可主动失效、需额外中间件）；JWT 放 `localStorage`（无状态但可被 XSS 读取）；JWT 放 HttpOnly Cookie（无状态且不可被 JS 读）。

**选择**：JWT，载体是 HttpOnly Cookie；同时兼容 `Authorization: Bearer` 供脚本与自动化测试使用。

**为什么改掉最初的"响应体返回 accessToken"**：`docs/api.md` v0.1 写的是响应体回传 token，等于把 HttpOnly 的意义抹掉。复核时统一改为 Cookie 下发，接口文档同步升到 v0.4。这条修正的记录在 `docs/adr/ADR-001-jwt-vs-session.md` 末尾。

**代价与复审条件**：JWT 无法主动吊销——需要"封号立即生效"时，必须引入 token 黑名单或改回 Session。当前课程场景没有该需求；一旦出现，复审本条。

## 6.2 ADR-002 排程引擎拆分与契约先行

**背景**：UC-03 预估 24 人时，超出单个 Issue 的可评审粒度，而 3 人需要并行。

**选择**：拆成选点（selector）、评分装箱（packer/scorer）、可行性（feasibility，规划中）三个子模块，先用 `engine/protocols.py` 定输入输出契约，再各自实现。`services/engine_bridge.py` 负责 ORM ↔ 纯 dataclass 的转换。

**代价**：契约变更要三方同步；中间层多一次对象转换。收益是 **engine 层可脱离数据库单测**——`backend/tests/test_scorer_units.py` 的 11 个用例不建库、不联网，2 秒内跑完。

## 6.3 ADR-003 贪心装箱 vs 整数规划

**背景**：15 天 × 最多 300 候选 POI，同时有硬约束（时间不重叠、必去必避）与软约束（五项加权）。

**备选**：ILP（OR-Tools）可给最优解但求解时间不可控；DP 在 15 天 × 300 点上状态空间爆炸。

**选择**：综合评分排序 + 按天贪心装箱。单次求解在毫秒级，失败可降级（减少景点数而不是超时）。

**代价**：**不保证全局最优**，可能错过更优组合。这是明确接受的取舍：课程项目的验收口径是"P95 ≤ 10s 且方案可用"，不是"最优"。若未来要求最优性，需要保留当前实现作为 baseline 再对比。

## 6.4 ADR-004 外部数据统一服务端代理

**背景**：7 个外部遗留系统，各有 API Key 与不同超时特性。

**选择**：全部经 `adapters/`，基座统一做超时、重试、缓存、降级、调用计数。

**代价**：adapter 层成为单点，任何外部接口变动都要改这里；但换来的是 Key 零暴露 + 配额可统计（`call_budget.py` 守住 BR-10 的单次 ≤ 60 次）。

**当前真实状态**：只有 `adapters/traffic.py` 接入了真实路径并带演示降级；其余适配器仍是契约（`○`）。**不能把"契约已定"说成"接口已对接"**——这是本册对第 1 次批阅"Mock 与真实服务需区分"的直接回应。

## 6.5 ADR-005 副本调整

**背景**：UC-05 调整后仍需可撤销，且不能污染已保存方案。

**选择**：调整在副本上做，用户确认后 `version+1`，旧版本置 `SUPERSEDED`，历史最多 10 个（BR-14）。

**代价**：存储翻倍（每版本一份完整行程）。当前单条行程数据量在 KB 级，可接受；若行程规模上升，需改成"基线 + 增量 diff"。

**状态**：**仅设计**。`adjust_service` 尚未实现，调整页目前是 mock 渲染（详见第 2 章 2.4.2）。这是第二阶段 #8 的核心工作。

## 6.6 ADR-006 拥挤度用统计模型

**背景**：需要给每个 POI 每天的拥挤度打分（0–100），但没有任何训练数据。

**备选**：LSTM / XGBoost 预测；或"历史同期均值 + 节假日系数"。

**选择**：后者。理由是可解释——用户看到"国庆假期 +40%"能理解，看到神经网络的输出只会觉得是黑箱；而且无训练数据时上 ML 属于包装。

**代价**：对突发事件（临时封路、演唱会）不敏感。缓解手段是 `CrowdIndex = UNKNOWN` 降级 + 界面提示，而不是硬猜。

## 6.7 ADR-007 技术栈整体切 Python

**背景**：初始方案是 Spring Boot + Vue 3，但三人 Java 熟练度低，CI 要维护两套运行时。

**选择**：FastAPI + Jinja2 + HTMX，单体服务端渲染。

**代价**：放弃组件化与前后端分离，页面交互复杂度上限降低（HTMX 只做局部替换）。对 8 个页面的规模是够的；若将来页面数翻倍或需要复杂交互，复审本条。

**收益是可量化的**：CI 从两套运行时降为一套；本地环境依赖从 4 项（JDK / Maven / Node / npm）降为 1 项（Python 3.11）。

## 6.8 决策之间的关系

```
ADR-007（切 Python 单体）
   ├→ 使 ADR-001 可以退化为 Cookie 方案（同域部署，无 CORS 凭证成本）
   ├→ 使 ADR-002 的"契约先行"可行（Python 侧 dataclass 契约轻量）
   └→ 使 CI 只需一套运行时，ADR-004 的代理层可被同一套测试覆盖

ADR-003（贪心） ← 依赖 ADR-002 拆出的 scorer/packer 边界
ADR-006（统计拥挤度） ← 依赖 ADR-004 的 traffic 代理取历史量
ADR-005（副本调整） ← 依赖 ADR-003 的方案结构可整体复制
```

一条被推翻的旧决策也记录在此：最初计划"前端直连第三方地图 API"（省一层代理），后因 Key 暴露与配额不可控改为 ADR-004。
