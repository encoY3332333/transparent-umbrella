# 个人工程贡献说明书（模板与说明）

> 课程考核 **B7「贡献说明书」占个人 30% 中的 4 分**，是唯一一份「由本人撰写、需要他人佐证」的材料。
> 它不是自我表扬，是**可核验的证据索引**——评审老师会拿它去对照 GitHub 上的 Commit / PR / Issue / Review 记录。

## 为什么必须早写

很多小组在答辩前一周才开始写，结果发现：

- 记不清某个 PR 为什么那么改
- 想不出「遇到的困难」——因为当时解决了就忘了
- 数据对不上（自己记得提了 5 个 PR，实际只合了 3 个）

正确做法：**每完成一个 Issse 就写一段**，答辩前只需要汇总。本目录的模板就是为了让这件事变成 10 分钟能做完的动作。

## 一份好的贡献说明书长什么样

| 特征 | 差 | 好 |
|---|---|---|
| 可核验 | 「负责了排程模块」 | 「实现了 `engine/schedule.py` 的 `plan_itinerary()`，#6 的 PR，`score_calculator.py` 新增 214 行」 |
| 有取舍 | 「用贪心算法实现了排程」 | 「在贪心和 ILP 之间选了贪心，因为 5 秒预算内 ILP 无法保证求解，见 ADR-003」 |
| 有反思 | 「学到了很多」 | 「接口设计时没考虑降级输入，导致 #5 的 Adapter 接口改了两次签名，返工约 2 小时」 |
| 有协作 | 「配合组员完成」 | 「评审了组员2 的 PR #12，指出 3 处问题：N+1 查询、缺少边界测试、异常吞掉」 |

## 目录

| 文件 | 说明 |
|---|---|
| `_template.md` | 个人贡献说明书模板，每人生成一份副本 |
| `【组长】.md` | 待填写 |
| `【组员1】.md` | 待填写 |
| `【组员2】.md` | 待填写 |

> 文件名直接改成真实姓名（如 `张三.md`），并在下方索引里同步更新。

## 硬性数据自查表

填完之后，逐项对照 GitHub 页面的实际数字。**任何一项不达标，个人总分 ×0.6**。

| 指标 | 考核下限 | 【组长】 | 【组员1】 | 【组员2】 |
|---|---|---|---|---|
| 有效 Commit 数 | ≥ 8 | | | |
| 合并的 PR 数 | ≥ 4 | | | |
| Closed Issue 数 | ≥ 4 | | | |
| 对他人 PR 的有效评审条数 | ≥ 6 | | | |
| 有效测试用例数 | ≥ 5（或 bugfix PR ≥ 2） | | | |

**2 项及以上未达标 → 个人总分 ×0.6。** 这条规则在考核方案里写得很明确，不要赌老师不查。

## 提交方式

每人一份 `.docx`（由 `.md` 导出或按模板排版），随最终交付包提交。同时保留 `.md` 在仓库中——Git 的提交历史本身就是「什么时候写的」的证据。

## 常见错误

1. **把小组的工作写成自己的**。评审老师会看 PR 的作者，一眼能看出来。
2. **只写做了什么，不写为什么**。技术决策的理由才是区分「执行者」和「工程师」的地方。
3. **隐瞒失败**。「这个方案后来被推翻了，原因是我没考虑到 XX」——这种段落是加分项，不是减分项，前提是它同时写了「我怎么发现的、怎么修的」。
4. **评审记录写成「已 Review，无问题」**。6 条有效评审是硬性下限，无效的评审（如只写了 LGTM）不算数。**建议每条评审至少指出一个具体问题或提出一个具体改进**，并附上文件和行号。
