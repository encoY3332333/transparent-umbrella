# ADR-006 拥挤度用统计模型，不用机器学习

- **状态**：已采纳
- **日期**：2026-11-09
- **决策人**：【组长】、【组员1】、【组员2】
- **关联 Issue**：#5（候选筛选与拥挤度计算）

## 背景

拥挤度 `CrowdIndex` 是排程评分的第二权重项（`w_crowd = 0.23`），直接影响"国庆去故宫还是去小众博物馆"这类决策，是本产品区别于普通攻略 App 的核心数据之一。

SRS 对它的定义（BR-21 / BR-22）：

- 取值范围 0–100（整数），越大越拥挤
- 计算式为 `CrowdIndex(p, d) = min(100, round(100 × HistVolume(p, d) / Capacity(p)))`
- 当 `HistVolume` 缺失时返回 `UNKNOWN`，排程取消该项惩罚（降级，见 `architecture.md` 6.2）

团队需要决定：`HistVolume(p, d)`（POI p 在日期 d 的历史游览量）怎么估。

## 备选方案

### 方案 A：机器学习时序预测（LSTM / XGBoost）

用历史人流量数据训练模型，输入特征包括日期、星期、节假日、天气、历史同期序列，输出预测游览量。

- 优点：能捕捉复杂非线性模式；如果数据充足，精度最高；答辩时"用了机器学习"听起来有分量
- 缺点（**决定性的**）：
  - **没有训练数据**。课程提供的"人流量服务"只有按天查询的接口，能取到历史数值，但拿不到"可训练的数据集"——没有明确的训练集/验证集划分，没有数据字典说明字段口径
  - **数据量不够**。单个 POI 的历史数据通常只有几百到几千条，覆盖不了节假日的稀疏样本，模型在最重要的场景（节假日预测）上最不可靠
  - **不可解释**。用户问"为什么这天显示拥挤度 92"，模型答不上来。而"解释"是本产品的差异化定位
  - **工程成本高**。要引入模型运行时或 ONNX 推理，本项目是纯 Python 单体，`docker compose` 要加一个服务，CI 要加一套环境与模型文件下载
  - **不可测试**。模型输出是浮点数，单测只能断言"在合理区间"，无法断言"给定输入必然产出 87"

### 方案 B：简单统计模型（历史同期均值 × 节假日系数）

```
HistVolume(p, d) = Avg(近 3 年同期同类日期的游览量) × HolidayFactor(d)
CrowdIndex(p, d) = min(100, round(100 × HistVolume(p, d) / Capacity(p)))
```

"同期同类日期"定义为：**同月份、同"工作日/周末/法定节假日"类型**。`HolidayFactor` 从配置表读取（如国庆 1.8、春节 2.2、普通周末 1.3、工作日 1.0）。

- 优点：
  - 纯计算，无外部依赖，无训练
  - **完全可解释**：能直接告诉用户"近三年 10 月 2 日平均 4.2 万人次，为承载量的 84%，国庆系数 1.8 后达到上限"
  - **可测试**：给定固定的历史数据和系数，输出是确定的整数，可以写精确断言
  - 计算量极小（一次批量查询后纯内存计算）
- 缺点：
  - **精度有限**。无法捕捉"某个 POI 因网红视频突然爆火"这类突变
  - **冷启动问题**。历史数据不足 1 年的新 POI 无法计算，只能返回 `UNKNOWN`

### 方案 C：直接用第三方返回的拥挤度

如果人流量服务本身提供"拥挤度"字段，直接透传。

- 优点：零实现
- 缺点：**第三方接口不提供该字段**（只给原始游览量）。而且即使提供，也无法按本系统的承载量口径归一化，不同 POI 的数值不可比

## 决策

**采用方案 B：历史同期均值 × 节假日系数。**

`HolidayFactor` 存 `strategy_parameter` 表，随策略版本管理（BR-20），管理员可在 UC-09 中调整。

## 理由

1. **方案 A 的前提不成立**。没有可训练的数据集，ML 方案不是"效果更好的选择"，而是"做不出来的选择"。硬上只能造一个假的数据集，那就是学术不诚实。
2. **方案 A 的不可解释性与产品定位冲突**。README 里的差异化定位写的是"解释为什么这么排"，拥挤度是排名前三的推荐理由之一。一个说不清缘由的数字，在 UI 上只能展示"拥挤度 92"，而方案 B 能展示"国庆系数 1.8，预计接近承载上限"。
3. **方案 B 的精度缺陷影响可控**。因为 `CrowdIndex` 只是五个评分项之一（权重 0.23），且最终由用户从 1–3 套方案中选择，单点预测偏差不会导致灾难性结果。"网红爆火"这类突变本来也不是任何离线模型能提前预测的。
4. **可测试性直接对应 B5 评分（测试与缺陷）**。方案 B 可以写"给定 3 年数据 + 国庆系数 → 断言输出 100"这样的精确单测，覆盖边界（`HistVolume` 为 0、超承载量、恰好等于承载量、数据缺失）；方案 A 只能写"输出在 0–100 之间"这种弱断言。
5. **方案 C 的前提也不成立**（接口无此字段），且归一化口径由本系统定义，本来就该自己算。

## 影响

- **正面**：
  - 纯内存计算，无额外依赖，`docker-compose.yml` 不用加服务
  - 输出确定，可写精确单测，可做"输入快照 → 输出快照"回归测试
  - 能生成自然语言解释，供前端展示推荐理由
  - `HolidayFactor` 可配置，答辩时可以现场演示"把国庆系数从 1.8 调到 1.2，行程推荐立刻变化"——这是个很好的演示点
- **负面**：
  - **冷启动**：运营不足 1 年的 POI 返回 `UNKNOWN`，排程时不参与拥挤度惩罚。这会让新 POI 相对"更受欢迎"，是一个已知的、可接受的偏差（对新 POI 友好，符合业务意图）
  - **无法预测突发**：已在 ADR 里坦承，不在产品承诺范围内
  - **"同期"定义需要数据支撑**：如果人流量服务只能按具体日期查，需要循环查询近 3 年同月同日，调用次数会上升。缓解：在 `#5` 里把"近 3 年同期"改为**一次批量接口调用取整月**，再在内存里按日期类型聚合，控制在 3 次调用内
- **后续动作**：
  - `#5` 的 Issue 里补一条验收标准：`CrowdIndexCalculator` 必须覆盖 5 个边界用例（0 值、等于承载量、超承载量截断至 100、历史缺失、系数缺失时用 1.0）
  - `#13` 策略配置页需支持编辑 `HolidayFactor` 表，并做"系数 ∈ [0.5, 5.0]"的范围校验
  - 若将来第三方提供了标准化拥挤度字段，回来写新 ADR 取代本条，本 ADR 状态改为"已取代"
