# ADR-002 排程模块拆分为 3 个子模块、契约先行

- **状态**：已采纳
- **日期**：2026-11-09
- **决策人**：【组长】、【组员1】、【组员2】
- **关联 Issue**：#4（编排入口）、#5（候选筛选与拥挤度）、#6（排程算法）、#7（预算迭代）

## 背景

UC-03「生成行程」是全系统的技术核心，SRS 里预估工作量约 24 人时，承担了 A3「功能与质量」16 分里的大部分内容。

但课程考核方案对 Issue 粒度有硬性要求：**单个 Issue 预估工时 2–8 小时**。一个 24 小时的 Issue 无法满足要求，也无法真实反映"某人在某个 PR 里做了什么"。

同时有个现实问题：三个人都要在 A3 上拿分，而排程算法如果由一个人从头写到尾，另外两人只能去做边缘功能，个人贡献 B1「任务闭环」和 B2「代码质量」的评分会严重失衡。

## 备选方案

### 方案 A：一个人做完整个排程引擎，另外两人做前端和管理端

- 优点：没有接口冲突，沟通成本最低；引擎内部设计可以随意重构
- 缺点：**工时集中在一个人身上**，违反 Issue 粒度要求；另外两人的代码贡献在核心链路上为零，A5「PR 与评审」可评审的内容也少；一旦这个人生病或有其他课业冲突，整个 A3 直接崩盘

### 方案 B：拆分模块，但边写边定接口

- 优点：三个人同时开工
- 缺点：**接口在开发中反复变**，A 写的 `select()` 返回 `List<POI>`，B 以为是 `List<Candidate>`，C 以为是分页对象，集成时大面积返工。三个人互相等对方"先定下来"，实际反而更慢

### 方案 C：先定接口契约（空壳实现 + 单测骨架），再并行填实现

1. 由 #4 的负责人先提交一份 `engine/` 的**协议（`typing.Protocol`）+ dataclass + 空实现（抛 `NotImplementedError`）+ 单测骨架（全部 `@pytest.mark.skip`）**
2. 合并后，三人各自在独立分支上填自己那块的实现和测试，彼此**不需要再看对方的实现代码**
3. 每块独立通过单测后，再在 #6 里做集成

- 优点：并行度高；接口变更需走 PR 并通知另外两人，成本可见；每人都有完整"写代码 → 写测试 → 提 PR → 被评审"的闭环
- 缺点：**必须先花 2–3 小时设计接口**；如果接口设计错了，三个人一起返工

## 决策

**采用方案 C。**

模块拆分与责任人：

| 子模块 | Issue | 职责 | 工时 |
|---|---|---|---|
| 编排入口 + 接口契约定稿 | #4 | `PlanService`、schema、`engine` 协议空壳、依赖装配、路由 | 6h |
| 候选筛选 + 拥挤度计算 | #5 | `CandidateSelector`、`CrowdIndexCalculator`、人流量 Adapter 对接 | 8h |
| 排程算法核心 | #6 | `ScoreCalculator`、贪心装箱、`FeasibilityChecker`、多方案生成 | 10h |
| 预算迭代 | #7 | `BudgetCalculator`、`BudgetIterator`、超预算降本策略 | 6h |

## 理由

1. **方案 C 的"额外成本"（2–3 小时的接口设计）是可回收的**。这 2–3 小时同时就是 #4 的工作内容，不是纯粹的损耗；而且接口一旦定下，三次 PR 评审的关注点从"你这段逻辑对不对"变成"你有没有遵守契约"，评审效率更高。
2. **方案 C 解决了 A 的死穴**：任何一个人的缺席只会让一个 6–10 小时的模块延期，而不是让整个 A3 停摆。
3. **方案 B 的失败模式在小组作业里极其常见**：三个人都觉得"等对方先定"，最后在截止日前两天才开始集成。方案 C 把"定接口"变成一个有 Issue、有 PR、有截止时间的具体任务，把它从"隐性前置条件"变成"显性交付物"。
4. **接口先行天然带来可测试性**。空壳 + `@Disabled` 的测试骨架入库后，每个人填实现时测试已经写好了名字和断言意图，写起来是"让红的变绿"，比"写完再想怎么测"质量高得多。

## 影响

- **正面**：
  - 三个人都能拿到核心链路的代码贡献，A3 与 B2 评分均衡
  - 接口契约本身成为 Code Review 的检查依据
  - `engine` 的输入是纯 dataclass 而非 ORM 实体，单测不需要建数据库连接，测试跑得快
- **负面**：
  - **#5 / #6 / #7 全部被 #4 阻塞**，串行等待 #4 合并后才能开工。缓解：#4 只做契约和空壳，不做实现，力争 1–2 天内合入
  - 接口设计不当会三人返工。缓解：#4 的 PR 必须三个人都 Approve，且评审时专门检查"这个签名能否支撑后续三块实现"
- **后续动作**：
  - #4 的 PR 描述里必须贴出 `engine` 协议完整签名与三个核心 dataclass 的字段表
  - 接口变更走**新 Issue + 通知另外两人**，不允许在实现分支里偷偷改签名
  - 集成测试放在 #6，覆盖"候选 → 评分 → 装箱 → 预算"的完整链路
