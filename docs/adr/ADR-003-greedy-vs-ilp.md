# ADR-003 排程算法用贪心装箱 + 综合评分，不用整数规划

- **状态**：已采纳
- **日期**：2026-11-09
- **决策人**：【组长】、【组员1】、【组员2】
- **关联 Issue**：#6（排程算法核心）

## 背景

行程规划本质上是一个**带时间窗、带预算约束、带容量约束的多目标调度问题**，教科书上有成熟的精确求解方法。团队在立项时确实讨论了要不要用精确算法。

输入规模（SRS 3.3 与 BR-08 已框定）：

- 行程天数 1–15 天
- 候选 POI 经过筛选后收敛到 20–300 个
- 每天可安排活动 1–8 个（含用餐与休息时段）
- 优化目标有 5 个，且**互相冲突**：偏好匹配度、天气适配度、拥挤度、通勤时长、费用

硬性性能指标（NFR-P1）：**行程生成 P95 ≤ 10 秒**，其中外部数据获取已占用约 3–5 秒，留给算法本身的时间只有 **5 秒左右**。

## 备选方案

### 方案 A：混合整数线性规划（ILP / OR-Tools CP-SAT）

把"POI p 是否安排在第 d 天第 s 个时段"建模为 0-1 变量 `x[p][d][s]`，约束包括：每天时长上限、每时段只排一个、通勤时长衔接、预算上限、必去 POI 必须排入。目标函数是五个指标的加权和。

- 优点：**理论最优**；约束表达力强，新增规则只改约束不改算法骨架；有成熟的求解器
- 缺点：
  - **求解时间不可控**。课程项目里没有调优求解器参数的经验，一旦在某个输入上超时，10 秒指标直接失守，而且难以在答辩时解释"为什么这次用了 30 秒"
  - **变量规模大**：300 POI × 15 天 × 6 时段 = 27000 个 0-1 变量，加上通勤衔接的额外变量，单个请求的内存与 CPU 成本对 `docker compose` 里的单机后端不友好
  - **需要额外依赖**（OR-Tools 是原生库，Windows / macOS / Linux 的 jar 不同，团队成员环境不一致会踩坑）
  - **单测难写**。验证"最优性"需要另写一个暴力枚举做对照，等于工作量翻倍
  - **无法向用户解释**。ILP 给出结果，但很难生成"为什么推荐这个而不是那个"的自然语言理由，而 SRS 要求每套方案附推荐理由（F5）

### 方案 B：动态规划

按天划分阶段，`dp[d][budget][state]` 表示前 d 天在剩余预算下的最优值。

- 优点：比 ILP 快，能得到近似最优
- 缺点：**状态空间会爆炸**。`state` 需要记录"哪些 POI 已访问"（2^300 不可能）、"当前所在位置"、"累计时长"，三者叠加后状态数远超可接受范围。必须做大量剪枝假设，剪枝一旦不成立结果就不保证，等于放弃了 DP 的理论优势

### 方案 C：贪心装箱 + 综合评分排序

1. **评分**：对每个 (POI, 日期) 组合算一个综合分
   ```
   Score(p, d) = w_pref·PrefMatch(p, tourist) + w_weather·WeatherFit(p, d)
               − w_crowd·CrowdIndex(p, d) − w_travel·TravelMinutes(prev, p)/30
               − w_cost·Price(p)/Budget
   ```
   默认权重 `w_pref=0.10, w_weather=0.25, w_crowd=0.23, w_travel=0.14, w_cost=0.28`（由问卷 Q5 的加权排序结果换算，和为 1）
2. **装箱**：按天依次遍历，每天从剩余候选里取分数最高的 POI 放入当前时段，扣除时长与费用，直到当日时长用尽
3. **校验**：`FeasibilityChecker` 检查必去 POI 是否全部排入、时间是否重叠、预算是否超限
4. **预算迭代**：若总费用超预算，按"性价比最低优先替换"迭代降本，最多迭代 N 轮

- 优点：
  - **复杂度 O(n²)**，300 POI × 15 天的规模实测在 1 秒内完成，5 秒预算绰绰有余
  - 只用 JDK 标准库，零原生依赖
  - **可解释**：每个 POI 的每一项得分都能算出来，可以生成"因天气晴朗加分""因国庆拥挤度 92 减分"这样的推荐理由
  - **易测试**：给定固定的候选集和权重，输出是确定性的，可以写断言
- 缺点：**不保证最优**。贪心可能因为早选了某个高分 POI，导致后面某个必去 POI 排不进去，只能靠"必去 POI 优先锁定"的预处理缓解

## 决策

**采用方案 C：贪心装箱 + 综合评分**，并在算法前加一步「必去 POI 锁定」（BR-09 要求必去 POI 必须排入，直接作为硬约束预置到对应日期的首选位置，不参与贪心竞争）。

权重不写死在代码里，存 `strategy_parameter` 表（F9），管理端可调，每次生成记录所用版本号（BR-20）。

## 理由

1. **性能指标是硬约束，最优性是软目标**。SRS 对"方案是否最优"没有任何承诺——用户要的是"一个说得通的行程"，不是"数学意义上的最优行程"。用不确定性极高的方案 A 去换一个用户根本感知不到的最优性，是错误的交换。
2. **NFR-P1 的 10 秒里有 3–5 秒被外部调用吃掉**，这个事实决定了算法预算只有 5 秒。方案 A 在 27000 变量的规模下，5 秒内得到**有质量保证**的解需要专业调优，超出团队能力边界。
3. **"可解释"是本产品的差异化卖点之一**。README 里明确写了差异化定位是"解释为什么这么排"。方案 C 的分数分解天然支撑这一点，方案 A 需要事后做归因分析，成本远高于收益。
4. **方案 B 的剪枝假设不成立**就不能叫"动态规划"了，只是在 DP 的壳里做贪心，那还不如直接把贪心写清楚。诚实地说：我们评估过 DP，结论是它在本问题上是个更贵的贪心。
5. **贪心的缺陷有明确、低成本的补丁**。 "早选高分挤掉必去 POI"这个问题，用"必去 POI 预处理锁定"就能解决大部分；残余的次优问题，通过"生成 1–3 套不同随机种子的方案让用户选"来缓解（F5 本来就要求多方案）。

## 影响

- **正面**：
  - 算法在 5 秒预算内稳定完成，不依赖任何原生库，三人环境一致
  - 单测可以用"手工构造的小规模候选集 + 预期排序"来断言，不需要对照暴力解
  - 每个 POI 的分数明细可直接返回给前端，用于展示推荐理由
- **负面**：
  - **不保证全局最优**，极端输入下可能出现"方案可行但不是最好"
  - **权重敏感**：权重配置不当会让某一项主导排序（如 `w_cost` 过大导致永远只推免费景点）。缓解：#6 实现时对每项做归一化到 [0,1]，#13 的策略配置页增加"权重合理性提示"
  - **贪心的顺序依赖**：改变候选集顺序可能改变结果。缓解：候选集在进入引擎前**按 poiId 稳定排序**，保证同输入同输出
- **后续动作**：
  - #6 必须写一个"输入固定 → 输出快照"的回归测试，防止后续优化悄悄改变排序结果
  - 若答辩中被问"为什么不用精确算法"，本 ADR 即为回答
  - 若将来 POI 数据量增长到万级，需重新评估——届时会写新 ADR 取代本条
