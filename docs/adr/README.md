# 架构决策记录（ADR）

> Architecture Decision Records。记录**为什么这么做**，而不是**做了什么**——后者看代码和 `docs/architecture.md` 就够了。
>
> 本目录的 ADR 一旦被后续 ADR 取代，**不修改原文**，只把 `状态` 改为 `已取代` 并指向新编号。这样评审和答辩时可以展示决策的演进过程。

## 什么时候要写 ADR

满足以下任一条就该写：

1. 涉及**技术选型**（框架、数据库、中间件、算法方案）
2. 决定**跨模块的契约或分层约束**
3. 有**明确的备选方案**，且取舍需要向别人解释
4. 事后如果推翻，会带来**较大返工成本**

不需要写 ADR 的：变量命名、页面配色、单个函数怎么写。

## 模板

新建时复制 `_template.md`，文件名格式 `ADR-00N-短横线小写英文简述.md`，N 从 001 递增，不复用。

## 状态说明

| 状态 | 含义 |
|---|---|
| 提议中 | 已写但团队未讨论通过，不应据此写代码 |
| 已采纳 | 团队确认，代码须遵循 |
| 已取代 | 被更新的 ADR 推翻，保留供追溯 |
| 已废弃 | 因需求变化不再适用，且无替代方案 |
