# ADR-005 行程调整在副本上执行，确认后覆盖

- **状态**：已采纳
- **日期**：2026-11-09
- **决策人**：【组长】、【组员1】、【组员2】
- **关联 Issue**：#9（行程调整）

## 背景

UC-05 支持四种调整操作：调序、替换、删除/新增、锁定后重排（BR-14）。SRS 对版本有两条规则：

- **BR-13**：每次保存调整结果生成新版本，`version + 1`
- **BR-14**：每个行程最多保留 10 个历史版本

同时在界面交互上，用户调整时是**边改边看**的（拖拽后立刻看到新的时间安排与冲突提示），改到满意才点"保存"。

这里有一个容易被忽略的设计问题：**用户拖了五次、最后全撤销，这算几个版本？**

## 备选方案

### 方案 A：直接改原对象，靠操作日志回滚

每次调整直接修改数据库里的 `activity` 记录，同时往 `operation_log` 表写一条"把 A 从第 2 天第 3 位移到第 3 天第 1 位"。撤销时反查日志执行逆操作。

- 优点：没有版本膨胀；数据只有一份
- 缺点：
  - **逆操作不总是存在**。例如"替换"操作的逆是"换回原来的 POI"，但如果原 POI 在此期间被管理员下架（`status` 改为 `OFFLINE`），就无法换回
  - **中间态会被别的请求看到**。用户拖拽是连续多次请求，其他设备刷新时看到的是半成品
  - **冲突清单的计算依赖已落库的状态**，即使最后要撤销，也要先写进去再算，写失败就脏了
  - 版本历史（BR-13）反而更难实现——要在日志里"重建"每个版本，等于把日志当数据用

### 方案 B：前端全内存调整，一次性提交

所有拖拽只改前端的 Pinia store，用户点保存时把整个行程结构 `PUT` 给后端。

- 优点：后端只处理最终态，逻辑简单；无中间态落库
- 缺点：
  - **冲突与重算必须在前端做**。通勤时长重算需要调地图服务（BR-15），而密钥在后端（ADR-004），前端做不了，只能调一次问一次，每次都要求后端返回整份重算结果但又不能落库——接口语义会变得别扭
  - 一次提交整份行程，**无法做细粒度校验和错误定位**（"第 3 天 14:20 的活动与第 2 天冲突"这种提示需要后端有明确的输入结构）
  - 前端要实现一套和后端等价的可行性校验，双份逻辑必然不一致

### 方案 C：后端在副本上执行，返回预览；确认后落库

1. 前端每次调整发 `PUT /api/itineraries/{id}/preview-adjust`，body 是一个**操作指令**（`{op: "MOVE", activityId: 42, targetDay: 3, targetIndex: 1}`）
2. 后端**不落库**：把 DB 里的行程反序列化为内存对象，在内存副本上应用操作，只重算受影响的相邻两项通勤时长（BR-15），跑 `FeasibilityChecker`，返回「调整后的完整行程视图 + 冲突清单」
3. 用户点"保存"时发 `PUT /api/itineraries/{id}/adjust`，同样的操作指令，后端在事务内正式应用并 `version + 1`
4. 用户点"撤销"时发 `PUT .../preview-adjust` 带反向操作，依旧只改内存副本

- 优点：
  - 撤销语义天然成立——因为什么都没落库
  - 无中间态，其他设备看到的始终是已保存版本
  - 校验与重算逻辑只有后端一份
  - 预览与保存复用**同一段应用操作的代码**，不会出现"预览说可以、保存时失败"
- 缺点：连续拖拽会产生多次请求，每次都要读一次 DB 并反序列化

## 决策

**采用方案 C。** 预览接口 `PUT /api/itineraries/{id}/preview-adjust` 与保存接口 `PUT /api/itineraries/{id}/adjust` 共用 `AdjustService.applyOperation()` 私有方法，区别仅在于是否包在事务里、是否写库。

## 理由

1. **"撤销"用方案 C 是免费的，用方案 A 需要逆操作**。方案 A 的逆操作在"原 POI 被下架"时失效，这不是理论风险——管理员下架 POI（UC-08）和用户调整行程（UC-05）是两条并发路径。方案 C 从根上不产生需要回滚的状态。
2. **BR-13 / BR-14 的版本语义变得更清晰**。版本只在下"保存"时产生，"用户拖了五次全撤销"＝零个新版本，符合用户直觉，也不浪费 10 个版本的配额。
3. **方案 B 的双份校验逻辑是必然的 bug 来源**。可行性校验规则在 SRS 里有 24 条业务规则，前端复刻一份等于维护两个真相源。而且 BR-15（只重算受影响相邻两项）的优化在纯前端做不到，因为前端拿不到通勤时长矩阵。
4. **性能可接受**。单次 preview 请求读一次行程（一次主查询 + 一次 activity 批量查询），行程最大 15 天 × 8 活动 = 120 条 activity，反序列化在毫秒级；通勤重算只调 2 次地图服务（命中缓存时 0 次）。NFR-P4 要求调序响应 ≤ 1.5 秒，余量充足。
5. 前端可以在拖拽时做**乐观更新**（立即渲染），同时发 preview 请求，返回后以服务端结果为准——既保证手感，又保证正确性来自单一真相源。

## 影响

- **正面**：
  - 撤销无需逆操作逻辑，无脏数据
  - 版本只在保存时产生，语义清晰
  - 预览与保存共用代码路径，"预览通过但保存失败"的概率大幅下降
- **负面**：
  - **请求次数增加**。一次拖拽 = 1 次 preview；用户快速拖动多次时会有请求风暴。缓解：#9 前端做 300ms 防抖；后端 preview 接口不加 `@Transactional`（只读），不占用连接
  - **`AdjustService` 必须无副作用**。`applyOperation()` 只能改内存对象，任何一处不小心写了库，整个设计就崩了。这是一个需要在 Code Review 时重点检查的点
  - 预览接口返回完整行程视图，响应体较大（120 条 activity ≈ 30KB），可接受
- **后续动作**：
  - `#9` 的 Issue 里明确写：`applyOperation()` 禁止调用任何 Mapper 的写方法
  - `#9` 必须写单测：同一操作序列在 preview 和 adjust 两条路径下产生**完全相同**的内存对象（用 `equals` 断言）
  - 前端 `#9` 补充乐观更新与防抖，写入 PR 的测试说明
