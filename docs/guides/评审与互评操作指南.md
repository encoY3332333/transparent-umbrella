## 三、Code Review 怎么做（B3 + B4 共 10 分）

### 3.1 规则

- 每人下限：**≥6 条有效评审**，分布在**≥3 个不同 PR**；
- 有效 = 行内评论，写清「**问题 + 原因 + 建议**」，指出文件与行号；只写 LGTM / Approve 不计；
- **禁止自评自合**：不能 Approve 自己的 PR；
- 结论三选一：Approve / Comment / Request changes。

### 3.2 交叉安排（谁都不能评自己）

| 评审人 | 评谁的 PR | 本轮具体对象 | 目标条数 |
|---|---|---|---|
| A | B 的 PR | #32 排程引擎、#33 覆盖率门禁 | 6 条（每个 3 条） |
| B | C 的 PR | #29 条件校验、#30 行程调整页、#31 POI 筛选 | 6–9 条（每个 2–3 条） |
| C | A 的 PR | #37 报告、#38 仓库同步、#39 评审机制 | 6 条（每个 2 条） |

### 3.3 界面操作（5 步）

1. 打开 PR → `Files changed`；
2. 鼠标移到目标代码行，点行号左侧蓝色 **+**；
3. 写评论：`问题：… / 原因：… / 建议：…`；
4. 右上角 **Review changes** → 选 Approve / Comment / Request changes → Submit review；
5. 收到 Request changes 后往**同一分支** push 新提交，PR 自动更新，不要重开 PR。

命令行等价（已配置 `gh` 的同学）：

```bash
gh pr review 32 --comment -b "app/engine/schedule.py:118 贪心装箱未处理暴雨日户外活动，违反 BR-09；建议在候选集过滤阶段先剔除 outdoor 类 POI"
gh pr review 32 --approve
```

## 四、组内互评怎么做（阶段末，20 分钟）

个人贡献 30% 不是「互相打分」，而是**用五个硬指标交叉核对**。坐下按表逐人核对，数字不对的当场改报告：

| 指标（课程下限） | A（2024A） | B（2024B） | C（2024C） | 核对方式 |
|---|---|---|---|---|
| 有效 Commit ≥8 | | | | `git shortlog -sne --all` |
| 合并 PR ≥4 | | | | PR 列表 + 作者筛选 |
| Closed Issue ≥4 | | | | Issue 列表按 Assignee 筛选 |
| 对他人 PR 评审 ≥6 条 | | | | 每个 PR 的 Reviews 计数 |
| 有效测试用例 ≥5（或 bugfix PR ≥2） | | | | `grep -c "def test_" backend/tests/*.py` |

**三条纪律**

1. **不看态度看记录**：不写「该同学认真负责」，写「PR #31 独立完成，2 条评审意见被采纳」；
2. **允许写差距**：B 的 #32/#33 CI 红灯、A 的 0 PR，都要写进互评表；
3. **互相签字**：填完后三人在同一张表上签字扫描，作为第 2 次报告的附件。

> 任意 2 项未达标，个人总分 ×0.6。当前 A 的 5 项里 4 项为 0，B 的评审为 0，C 的合并 PR 为 0——
> 三人都贴着风险线，所以这一轮评审不是形式，是必须补的数据。
